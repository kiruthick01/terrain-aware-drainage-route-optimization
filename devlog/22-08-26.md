three decisions to make before writing any of the checklist:

1. **hyetograph.** scenarios.json only has daily totals (e.g. 250mm/day).
   hec-ras rain-on-grid wants a time-distributed series, not a single
   number. going with a synthetic scs type ii 24h shape rather than
   chasing real sub-daily records - imd's grid is daily-only anyway so
   there's no real sub-daily data to source for this zone. documented as
   an assumption, same as everything else the proxy already flags.

2. **losses.** proxy uses a flat runoff coefficient (0.75). switching to
   scs curve number instead, derived from osm land use - more physically
   real and it reuses the same land-use layer manning's n needs anyway.

   this one has a real consequence: engine.py's docstring already warns
   the "equivalent rainfall" interpolation trick (folding runoff_coeff
   into an adjusted rainfall value) is a property of the proxy's math
   specifically, and real hydraulics won't obey it. so switching to CN
   breaks the current 1-slider interpolation.

   fix: precompute 3 antecedent moisture classes (CN-I/II/III, i.e.
   dry/normal/wet) per rainfall scenario instead of 1 run. 5 scenarios x
   3 = 15 hec-ras runs instead of 5. engine interpolates over 2 axes
   (rainfall x wetness) instead of 1. frontend runoff slider survives,
   just gets relabeled "soil wetness."

3. **mesh resolution.** 10m cells - 3x finer than the 30m dem, actually
   gives a reason to prefer this over the proxy spatially. accepted that
   runs take longer (minutes each, times 15); fine since everything's
   precomputed offline same as phase 2a.

2b.3 turned into a longer detour than expected. spent a good while trying
to actually source the real NRCS Type II 24-hr table (the 6-min-increment
ordinate list) instead of typing it from memory, since this is a real
input to a hydraulic model and getting it wrong silently felt worse than
not having it. every source i could find - the actual NRCS/USDA PDF
(directives.nrcs.usda.gov), oregon DOT's hydraulics manual, the nctcog
iswm manual - turned out to be scanned images, not real text, and there's
no OCR available here to read them. tried a bunch of secondary sources
(bentley docs, hec-hms wiki, scribd) that all *described* the table
without actually including the numbers.

decided not to guess. instead built a parametric approximation: a
logistic curve centered on hour 12, calibrated (via brentq root-find on
the steepness parameter) so exactly 40% of the daily total falls in the
one hour around the peak - that specific number (~40-43%) was the one
thing every source agreed on even without the full table, so it's the
one number worth trusting. reproduces the actual character of a type II
storm (long quiet buildup, one sharp burst near the middle, quick taper)
without pretending to ordinate-level precision i can't check. documented
this pretty bluntly in the module docstring - if track b ever needs real
NRCS-table fidelity (like validating against dec 2015 in phase 3), someone
should go find an OCR'd copy and swap the function body; nothing downstream
cares how the shape was made, only the output contract.
